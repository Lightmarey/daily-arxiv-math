# 运维与迁移

## 配置与抓取

生产展示配置保存在 D1，应用运行时不从文件系统读取配置。`config.local.json` 仅用于本地开发和自动化输入，不得提交。配置版本是规范化 JSON 的 SHA-256；Python 与 TypeScript 必须生成相同值。每个任务启动时固定一份配置快照，旧版本批次返回 HTTP 409。

`/api/ingest/state` 按当前 `fetchCategories` 返回独立游标。每类从游标前 72 小时重叠抓取，以覆盖延迟和修订；失败分类不生成零统计、不推进游标，下次任务继续追补。一个分类失败不阻止其他分类完成发布。显示已停抓分类合法，停止抓取或从展示移除都不删除历史。

所有 arXiv HTTP 请求由 `scripts/arxiv_http.py` 统一保证跨进程相邻请求至少四秒、遵守 Retry-After，并为每次运行限制累计等待预算。官方 New/Cross-list 清单是公告事件依据；Replacements 不计发文量。只有找到相应公告区且为空才能记零，无法证实的日期保持 missing。

## V3 数据迁移

迁移 `0002_lonely_chamber` 建立通用配置、分类报告、分类公告、分类发文量和分类运行表，并删除旧的 `report_entries`、`daily_volume`、`announcement_days`、`automation_runs`。旧几何报告、统计和运行状态不迁移；共享 `papers` 元数据保留。迁移 `0003_ingest_config_guard` 增加事务内配置校验触发器。迁移 `0004` 为 V3 报告增加 `proof_outline_json`；旧行默认记为尚未补读正文。此前被写成“未见披露”但没有核查来源的记录改为 `not_checked`，避免把未核查误报成未披露。

迁移 `0005` 在同一 D1 批次开始处比较分类、公告日和完成时间；已有更新的成功批次时以 409 拒绝旧批次，旧批次不能先删除较新的正文分析或回退 coverage。

这是有意的 clean replacement。`scripts/check_migrations.mjs` 只允许 `0002_lonely_chamber.sql` 中四条精确旧表删除，其他破坏性 SQL 仍会失败。生产应用前应备份 D1，并在副本执行全套迁移和 V3 冒烟。迁移失败时 D1 单批次回滚；保持旧应用并从备份恢复。迁移成功后不能再用旧应用写入。本轮不执行生产迁移。

## 健康与核对

- `/api/health` 只按当前抓取分类核对最近成功日、expected/published/数据库数量、发文量和游标。空抓取范围是正常空闲状态；数据库不可用仍为 degraded。
- `/api/volume` 中 `null` 表示缺失，`0` 表示官方确认零篇。周一至周五和所有请求分类都有统计时，周趋势才完整。
- `python scripts/verify_production.py --site <地址> --daily-outcome <同一计划时段结果> --scheduled-for <计划时段>` 先验证日报结果，再从 health 取得抓取范围，从公开配置取得展示范围。两者不同时，分别核对抓取健康趋势和展示趋势，不能直接比较不同分类集合的周对象；`--check-arxiv` 只供独立人工审计。
- 匿名读取 `/api/ingest/state` 或写入任何 ingest 接口必须返回 401；V1/V2 通过鉴权后返回 410。

工作日上海时间 14:30 执行核验。命令只输出日期、分类和数量摘要，不输出论文正文、鉴权头或完整写入载荷。任何失败都使自动任务失败并通知；成功保持静默。

## 静态镜像

Sites 和 D1 是权威数据源。静态 schema v2 保存 `data/config.json`、公开配置快照、按分类 coverage、最近十个完整公告日和两年趋势。一个 V3 文件只证明一个分类完整；离线同步必须提供同日所有仍抓取且显示的分类批次，或与已有分类快照聚合。已停抓但继续显示的分类在新公告日标记 `not_collected`，历史日期仍可访问。静态内容不得含阅读偏好、抓取范围、令牌或写入载荷。

公开镜像发布不是本地日报的一部分，必须由单独、显式授权的发布任务执行。该任务用 `scripts/publish_static_mirror.sh` 在临时 worktree 更新 `daily-content`；该分支与 `main` 是无关历史，只允许 Markdown、JSON 和说明文件，禁止强推和删除。脚本须持有本地锁，先做内容完整性、链接和敏感信息检查，再提交并快进推送。镜像生成、推送或触发失败只使该发布任务失败，不回滚已经完成的本地 D1 写入或分类游标。

`Arxiv Brief Pages` 从受保护 `main` 读取可信生成器，确认请求的 40 位完整 SHA 属于 `daily-content` 历史后再检出内容。推送后用精确内容 SHA 触发，并检查首页、日期归档、论文详情、筛选、数学渲染、XSS 转义和 26/104 周趋势切换。恢复旧镜像时手动运行同一工作流并输入已验证的旧 `daily-content` SHA，不改 D1。

## 发布门禁与回滚

1. 获取 `origin/main`，固定完整 Git SHA，并确认 `CI / gate` 成功。
2. 用 `scripts/release_gate.py` 比对候选 SHA、当前生产 SHA 和 CI 结果；只有 `deploy` 才继续。
3. 在临时干净 worktree 运行 `npm ci` 与 `npm run ci`，保存构建和配置版本证据。
4. 记录当前可恢复版本，再发布同一 SHA；发布后核对平台记录的 SHA，运行生产核验。
5. 代码冒烟失败时，仅在数据库 schema 兼容时恢复发布前保存版本；数据新鲜度或单分类采集失败只报警和追补，不逆向修改 D1。

回滚时先确认目标应用与当前 D1 schema 兼容，再选择最近的已验证版本，核对其 Git SHA、版本标签和归档哈希，直接重新部署保存产物而不重新构建。本次破坏性 V3 迁移完成后，不能只把应用回退到 V1/V2；跨 schema 回退必须在单独上线任务中同时恢复迁移前 D1 备份。完成后运行核心接口冒烟并记录目标与原因。公开版本切换仍须遵循发布审批；本轮不执行发布、生产迁移、Pages 推送或定时任务切换。
